# CRM V1 数据结构

每个实体模型位于 `backend/models/` 下的同名文件，统一入口为 `backend.models`；公共主键和时间字段位于 `backend.models.mixins`，数据库基类、延迟创建的连接池及 FastAPI 会话依赖位于 `backend.database`。
导入模块不会连接数据库，FastAPI 启动时也不会自动建表。
当前项目尚未配置 Alembic，本次不新增迁移框架。

## 表与关系

所有表都有 `id`、`created_at`、`updated_at`。

| 表 / 模型 | 业务字段 | 外键关系 |
| --- | --- | --- |
| `users` / User | name、email（唯一） | companies、opportunities、activities、tasks 的父表 |
| `companies` / Company | name | owner_id → users，必填 |
| `contacts` / Contact | name、email?、phone? | company_id → companies，必填 |
| `opportunities` / Opportunity | name、amount?、stage、probability?、expected_close_date? | company_id → companies、owner_id → users，均必填 |
| `activities` / Activity | summary、notes?、occurred_at | performed_by_id → users，必填；company_id、opportunity_id 可空 |
| `tasks` / Task | title、description?、status、due_at | assignee_id → users，必填；company_id、opportunity_id 可空 |

`?` 表示可空。所有关系都有双向 `relationship` / `back_populates`。
User → Company、Opportunity、Activity、Task；Company → Contact、Opportunity、Activity、Task；Opportunity → Activity、Task 均为一对多。

## 关键约定

- 主键使用 PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`；外键建索引。
- Company 和 Opportunity 分别指定 owner，不强制两者相同，允许公司负责人和商机负责人不同。
- `amount` 使用 `NUMERIC(18, 2)`，Python 使用 `Decimal`；非负，NULL 表示尚未估算，0 表示明确为零。V1 使用业务统一币种，不增加多币种换算。
- `probability` 使用 0–100 的整数百分比，可空表示未知；不根据 stage 自动推算，不冗余存储加权金额。
- OpportunityStage：NEW（默认）、QUALIFIED、PROPOSAL、NEGOTIATION、WON、LOST。
- TaskStatus：TODO（默认）、IN_PROGRESS、DONE、CANCELED。两类枚举都使用 PostgreSQL 原生 ENUM，默认值也写入数据库。
- Activity 的 `performed_by` 表示互动执行人，`occurred_at` 是调用方明确提供的已发生互动时间，不使用创建时间替代，也不添加待办状态。
- Task 的 `assignee` 是待办负责人；`due_at` 必填，允许保留已逾期截止时间。后续接口负责校验 Activity 的发生时间等动态业务规则。
- Activity / Task 可独立存在或只关联 Company；关联 Opportunity 时必须同时指定 Company，且公司必须与商机所属公司相同。复合外键及 CHECK 在数据库中强制该规则，Opportunity 的 `(id, company_id)` 唯一约束是该外键所需的目标键。
- ORM 赋值时显式指定 `company` 和 `opportunity`；各 relationship 只写入自己的外键，避免互相覆盖。修改商机所属公司时也会受已有互动和任务的复合外键保护。
- 删除策略统一 `RESTRICT`，不级联删除业务记录，也不自动清空历史关联。需要先显式解除或处理关联，才能删除父记录。
- 时间戳使用 `TIMESTAMP WITH TIME ZONE`，应用应传入带时区时间；`expected_close_date` 使用纯日期。
- `created_at` / `updated_at` 由数据库提供初始值；SQLAlchemy UPDATE 自动带上 `updated_at=now()`。这不是数据库触发器，直接执行原始 UPDATE SQL 时需自行更新该字段。参见 [SQLAlchemy 默认值文档](https://docs.sqlalchemy.org/en/20/core/defaults.html)。
- 本次仅实现数据层，不引入认证密码、RBAC、额外业务实体、接口或 Pydantic 请求/响应 schema。

## 初始化数据库

`.env` 中的 `DATABASE_URL` 应使用已有的 `postgresql+psycopg://...` 格式。
在项目根目录执行：

```bash
docker compose up -d --wait postgres
uv run --env-file .env python -m backend.init_db
```

命令使用事务创建六张表、枚举、索引及约束，可重复执行。
`create_all` 仅创建缺失表，不修改已存在表的列或约束，不是迁移工具。
以后调整已部署数据库结构时，应另行引入 Alembic migration。

后续 FastAPI 同步端点可通过 `Depends(get_session)` 获取 Session；写操作显式 `session.commit()`，离开依赖时关闭会话并回滚未提交事务。

## 验证

不依赖数据库的映射与 PostgreSQL DDL 检查：

```bash
uv run python -W error -m unittest discover -s tests -v
```

真实 PostgreSQL 测试（使用 `.env` 的数据库连接）：

```bash
uv run --env-file .env sh -c 'TEST_DATABASE_URL="$DATABASE_URL" python -W error -m unittest discover -s tests -v'
```

也可自行提供 `TEST_DATABASE_URL` 指向测试数据库。测试账号需要建 schema 权限。
每个集成测试使用随机独立 schema，并在结束后回滚整个事务，不修改已有业务表。
覆盖真实建表及重复初始化、Decimal 精度、时间戳与状态默认值、关系往返读取、非法值拒绝、公司/商机错绑拒绝、已关联父记录的删除保护。
未设置 `TEST_DATABASE_URL` 时，五项集成测试会明确跳过；离线检查通过不能替代真实数据库测试。
